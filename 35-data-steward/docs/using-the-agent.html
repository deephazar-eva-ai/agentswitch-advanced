Using the Data Steward agent

The agent reads parties and items on one system, finds likely duplicates, answers a few fixed questions about the data, and checks that each item's preferred vendor exists. This page shows how to run it and how to read everything it gives back.

It only readsIt never changes a record. A person makes every change, through the platform, with approval.
Fixed rules, no AI modelThe same data and the same private files give the same pairs and scores every time.
It cannot be talked into actingA request it does not recognise is refused before anything is read.

Four jobs

Pick a job to see its command. The first three are the duplicate workflow; the fourth is how the course harness talks to the agent.

uv run python -m data_steward.dedupe --instance suryodaya

Reads every party and item on one system and writes three private files to local/. Run it on both systems before you export. More in step 1.

File to edit by hand (the agent reads it and never writes it):

local/dedupe-labels.json

Give each pair you have judged a verdict. A label records intent only: it changes no score and no record. More in step 2.

uv run python -m data_steward.results

Makes results/dedupe_pairs.json from the saved reports, with no platform call. Needs a report from both systems. More in step 3.

uv run python -m data_steward.dedupe --instance suryodaya \
  --prompt "Which are the items that have no category?"

The harness adds --prompt to every task. The agent answers only the forms it recognises and refuses everything else. More in step 4.

1

Run the duplicate report

uv run python -m data_steward.dedupe --instance keystone
uv run python -m data_steward.dedupe --instance suryodaya

Each run writes three files, readable only by your account, into the git-ignored local/ folder, because they hold real party data:

local/dedupe-<system>.jsonThe full report: the record of truth.
local/dedupe-<system>.mdThe same report as a page to read.
local/dedupe-<system>-pairs.jsonEach listed pair: pair id, the two record ids, score and band.

Two optional private files in local/ change what the report shows: test-tags.txt and dedupe-labels.json (below). To reproduce someone else's report, get both from them privately.

Standard output is a summary with counts and the run's details only (no record data), safe to paste into a pull request; its last line names the files. If a run fails while reading, the earlier files stay as they were. If it fails while writing, all three are removed, so old and new files are never mixed.

What a score means

review
✓
00.60.91

Below 0.6: counted, not listed. From 0.6 to below 0.9: review. 0.9 and above: propose, unless a rule holds the pair back.

Scores are rule scores, not probabilities. A pair can score 1.0 and still sit in review when a rule holds it back; the report gives the reason. How a pair is scored, step by step: How duplicates are found.

How to read the report

Propose Proposed merges

Pairs scoring 0.9 or more with nothing holding them back.

Review Pairs to review

Pairs scoring 0.6 or more that a person should judge. When a rule holds a pair back from propose, the reason is shown (for example, different roles or different phone numbers); a score from 0.6 to below 0.9 lands here without one.

Keep The suggested record to keep

Every pair suggests which record to keep: the one with more linked records (counted for proposed merges only), then the older, then the one with more fields filled, then the first id in text order. It is only a suggestion.

Test Test-record pairs

Pairs where a name carries a confirmed test-run tag, one row each. The tags come from the private file local/test-tags.txt, one per line, added by a person only after a read confirmed it; without it, these pairs are not set apart.

The summary counts them apart from the bands, but the export still lists them, so an export can hold pairs even when the report shows no ordinary proposal.

Labelled Pairs already labelled

One row each, under their band (or under test-record pairs, for those). Full details of every pair are in the .json report.

Out Pairs ruled out

Pairs that scored high but can never be merged, with the reason: for example, different companies, or a party flagged as an allowed duplicate.

Limits Omissions and limits

What was not listed and why: low scores, records withheld for privacy, values shared too widely to count.

Orphans Items whose preferred vendor is missing

"Not found among the parties this login can list" means the vendor id names no party this login can read. A party created after the party table was read can also show up here.

If the party table was cut off, the check says it was not run. If only the item table was cut off, the count is a lower bound.

If a table was cut off (too many rows to read), the report says so. Rows beyond the cut were never compared, so a missing pair does not prove two records are different.

2

Review pairs

Write your verdicts in local/dedupe-labels.json. Copy each pair id exactly as the report shows it: the two ids are in a fixed order, so do not swap them.

{
  "party:<first id>:<second id>": "accepted",
  "item:<first id>:<second id>": {"label": "rejected", "note": "different sizes"}
}
  • Only accepted and rejected. With any other value the next report run stops (a local run shows a traceback whose last line names the bad entry), and the export stops with could not export: dedupe-labels.json is not valid: each label must be accepted or rejected.
  • A label changes no score, band or suggestion, and no record.
  • The export reads this file fresh each time, so a new label counts at the next export. Run the report again only to see the labels in it.

results/dedupe_pairs.jsoncommit in a pull request
  • It calls nothing on the platform. One entry per pair: kind, id_a, id_b, confidence, reason, and no names or other record values.
  • Pairs labelled rejected are left out; test-record pairs are listed, their reason ending "test-run records"; a review pair's confidence is 0.6 at most.
  • Standard output is counts only, then the file's path, including any rejected label that matches no pair in the reports used (often a typo).
  • It refuses a report from another rules version or with a cut-off table, and then leaves the earlier file as it was. Never edit the file by hand.

Needs both systems. With a report missing it stops with could not export: no saved report for <system>: run the scan first. --instance keystone exports one system and replaces the results file with that system's pairs alone: use it for a check, not for the file you commit.

4

Ask it a question

The course harness runs the agent once per task with the request added as --prompt, and you can do the same. A request with --prompt writes nothing to local/ and ignores local/test-tags.txt and local/dedupe-labels.json. Each sentence (ending in ., !, ? or ;) must match a recognised form as a whole; case, extra spaces and apostrophes do not matter.

How a request is read

The request is free text, but it is never run as code.

  1. It arrives as one string. The harness starts the agent with a list of arguments, not through a shell, and adds --prompt and the request text at the end. On your command line, the quotes keep the sentence together. Python's argparse stores it as a plain string; nothing evaluates it: no eval, no shell, no AI model.
  2. The record ids are taken out first, by their exact shape (8-4-4-4-12 hexadecimal characters).
  3. The rest is tidied and split into sentences: lower case, single spaces, apostrophes removed, split at . ! ? ;.
  4. Each sentence must match one known form in full. "scan these six parties for duplicates" matches the scan form; "do not change any record" matches a safety form. One sentence that matches nothing refuses the whole request, before any setting, login or call.
  5. Only a small, fixed choice comes out: scan, recount or refuse; party or item; the ids; which question. That choice drives the code. The text is never printed back or sent to the platform; ids go out only as values in read-only list calls.

Try some requests

Tap a request to see what the agent does with it. Each verdict was checked against the agent on 23 Nov; this page only shows it. To use an example, replace each <id> with a full record id.

A reliable way to write a scan request

Every sentence must match a recognised form. Write one read sentence, then the record ids at the end, after a colon as the harness writes them, separated by commas. Use the full 36-character record ids, not a pair id, with no brackets or quotes. Two shapes are recognised:

  • look through, scan, check or review "these/the/those", an optional number, then parties, items, records, party records or item records, then "for duplicates", "for duplicate pairs" or "for duplicate records", optionally ending "and note / report / list what you find";
  • find, identify or list "duplicate" parties, items, records, party records or item records, "in" or "among" "these/the/those" (optional number) parties, items, records, party records or item records, optionally ending "and note / report what you find" or "and record your merge proposal". Only this shape accepts recording a proposal.

Naming parties and items in one request is refused. "Records" alone means each id is looked up as a party, then as an item. Safety sentences may stand beside a scan or a recount, never alone: "Make no changes.", "Do not make any changes.", "Do not change any record." (or delete, merge, create, update, edit, modify or remove; and record, item, party or approval request), "Leave every party record exactly as it is.", and the harness's own lists such as "Do not merge, delete, or change any record."

Exit codes and error lines

    

      
0Finished
A completed report or export, or a prompted run that returns a done, failed or refused claim.

      
1Could not run
Login failed or settings missing; a platform outage or error, including during a scan; a lost connection; a recount table cut off, or a field the rule needs absent from every row of a non-empty table; an export that cannot run. One line on standard error, such as could not run: …, platform problem: …, connection or file problem: … or could not export: …. It never quotes a platform reply.

      
2Command-line mistake
Such as an unknown --instance value. The usage message is shown.

    

    
Under the harness, an error the agent does not expect shows as internal error: <error type>; a local run shows the traceback. For the harness a non-zero exit is an infrastructure failure, which is why a scan that cannot read its records, or runs out of time, says so and exits 0, while a platform outage still exits 1. On a single row, a missing contact, category or vendor value counts as blank, and a party with no privacy state is left out of party recounts.

  


  

    
Limits worth knowing

    
    
      
  • Matching is by rules, so some duplicates are missed: spellings further apart than a letter or two ("Lakshmi" and "Laxmi"), abbreviations ("SS" for stainless steel), initials.
    • 
      
  • A scan compares only the records named, so its pairs can differ from the full report, which sees the whole table.
    • 
      
  • A reworded question is refused. A new wording has to be added to the agent and its tests.
    • 
      
  • Recounts answer what is filled in, not what is true: a placeholder phone such as +91 0000000000 counts as a phone.
