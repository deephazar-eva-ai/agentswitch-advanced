Using the Data Steward agent

The agent reads parties and items on one system, finds likely duplicates, answers a few fixed questions about the data, and checks that each item's preferred vendor exists. This page shows how to run the agent and how to read its output.

It only readsThe agent never changes a record; a person makes every change through the platform with approval.
Fixed rules, no AI modelUsing the same data and the same private files produces the same pairs and scores every time.
It cannot be talked into actingThe agent refuses any unrecognised request before reading anything.

Four jobs

Select a job to see its command. The first three jobs make up the duplicate workflow; the fourth is how the course harness talks to the agent.

uv run python -m data_steward.dedupe --instance keystone
uv run python -m data_steward.dedupe --instance suryodaya

Reads every party and item on one system and writes three private files to local/. Run this on both systems before exporting. More in step 1.

File to edit by hand (the agent reads it and never writes to it):

local/dedupe-labels.json

Give each pair you have reviewed a verdict. A label records intent only, and it changes no score or record. More in step 2.

uv run python -m data_steward.results

Creates results/dedupe_pairs.json from the saved reports without calling the platform. Requires a report from both systems. More in step 3.

uv run python -m data_steward.dedupe --instance suryodaya \
  --prompt "Which are the items that have no category?"

The harness adds --prompt to every task. The agent answers only the forms it recognises and refuses everything else. More in step 4.

1

Run the duplicate report

uv run python -m data_steward.dedupe --instance keystone
uv run python -m data_steward.dedupe --instance suryodaya

Because they hold real party data, each run writes three files—readable only by your account—into the git-ignored local/ folder:

local/dedupe-<system>.json
The full report and record of truth.
local/dedupe-<system>.md
The same report formatted as a readable page.
local/dedupe-<system>-pairs.json
Each listed pair, with its pair id, the two record ids, score, and band.

Two optional private files in local/ change what the report shows: test-tags.txt and dedupe-labels.json (described below). To reproduce someone else's report, get both files from them privately.

Standard output prints only a summary with counts and run details (no record data), so it is safe to paste into a pull request; its last line names the files. If a run fails while reading, the earlier files stay as they were. If it fails while writing, all three are removed so old and new files are never mixed.

What a score means

✓
00.60.91

Below 0.6: counted, not listed. From 0.6 to below 0.9: review. 0.9 and above: propose, unless a rule holds the pair back.

Scores are rule scores, not probabilities. A pair can score 1.0 and still sit in review when a rule holds it back; the report gives the reason. For how a pair is scored step by step, see How duplicates are found.

How to read the report

ProposeProposed merges

Pairs scoring 0.9 or more with nothing holding them back.

ReviewPairs to review

Pairs scoring 0.6 or more that a person should judge. When a rule holds a pair back from propose, the reason is shown (for example, different roles or different phone numbers). A score from 0.6 to below 0.9 lands here without one.

KeepThe suggested record to keep

Every pair suggests which record to keep, chosen in this order: the one with more linked records (counted for proposed merges only), then the older record, then the one with more fields filled, and then the first id in text order. It is only a suggestion.

TestTest-record pairs

Pairs where a name carries a confirmed test-run tag, listed one per row. The tags come from the private file local/test-tags.txt, one per line, added by a person only after a read confirmed it; without this file, these pairs are not set apart.

The summary counts them separately from the bands, but the export still lists them. As a result, an export can hold pairs even when the report shows no ordinary proposal.

LabelledPairs already labelled

Listed one per row under their band (or under test-record pairs, for those). Full details of every pair are in the .json report.

OutPairs ruled out

Pairs that scored high but can never be merged, along with the reason—for example, different companies or a party flagged as an allowed duplicate.

LimitsOmissions and limits

What was not listed and why: low scores, records withheld for privacy, or values shared too widely to count.

OrphansItems whose preferred vendor is missing

"Not found among the parties this login can list" means the vendor id does not name any party this login can read. A party created after the party table was read can also show up here.

If the party table was cut off, the check reports that it was not run. If only the item table was cut off, the count is a lower bound.

If a table was cut off because there were too many rows to read, the report says so. Rows beyond the cut were never compared, so a missing pair does not prove two records are different.

2

Review pairs

Write your verdicts in local/dedupe-labels.json. Copy each pair id exactly as the report shows it. The two ids are in a fixed order, so do not swap them.

{
  "party:<first id>:<second id>": "accepted",
  "item:<first id>:<second id>": {"label": "rejected", "note": "different sizes"}
}
  • Use only accepted and rejected. Any other value stops the next report run (a local run shows a traceback whose last line names the bad entry) and stops the export with could not export: dedupe-labels.json is not valid: each label must be accepted or rejected.
  • No effect on scores or records. A label does not change any score, band, suggestion, or record.
  • Changes apply at the next export. The export reads this file fresh each time, so a new label counts at the next export. Run the report again only to see the labels in it.

results/dedupe_pairs.jsoncommit in a pull request
  • No platform calls or record values. The export calls nothing on the platform. It writes one entry per pair with kind, id_a, id_b, confidence, and reason, and no names or other record values.
  • Filtering and pair rules. Pairs labelled rejected are left out. Test-record pairs are listed, with their reason ending "test-run records". A review pair's confidence is 0.6 at most.
  • Standard output. Standard output shows counts only, followed by the file's path, including any rejected label that matches no pair in the reports used (often a typo).
  • Version and format checks. The export refuses a report from another rules version or with a cut-off table, leaving the earlier file unchanged. Never edit the file by hand.

Needs both systems. If a report is missing, the export stops with could not export: no saved report for <system>: run the scan first. Using --instance keystone exports one system and replaces the results file with that system's pairs alone. Use it for a check, not for the file you commit.

4

Ask it a question

The course harness runs the agent once per task and passes the request with --prompt; you can do the same. A request run with --prompt writes nothing to local/ and ignores local/test-tags.txt and local/dedupe-labels.json. Each sentence (ending in ., !, ? or ;) must match a recognised form in full; case, extra spaces and apostrophes do not matter.

How a request is read

The request is free text, but it is never run as code.

  1. It arrives as one string. The harness starts the agent with a list of arguments rather than through a shell, adding --prompt and the request text at the end. On your command line, quotes keep the sentence together. Python's argparse stores it as a plain string, and nothing evaluates it: no eval, no shell, and no AI model.
  2. The record ids are taken out first, matched by their exact format (8-4-4-4-12 hexadecimal characters).
  3. The rest is tidied and split into sentences: converted to lower case, reduced to single spaces, stripped of apostrophes, and split at . ! ? ;.
  4. Each sentence must match one known form in full. For example, "scan these six parties for duplicates" matches the scan form, and "do not change any record" matches a safety form. If any sentence matches nothing, the whole request is refused before any setting, login or call.
  5. Only a small, fixed set of choices comes out: whether to scan, recount or refuse; party or item; the ids; and which question. That output drives the code. The request text is never printed back or sent to the platform, and ids go out only as values in read-only list calls.

Try some requests

Tap a request to see what the agent does with it. Each verdict was checked against the agent on 23 Nov; this page only shows those verdicts. To use an example, replace each <id> with a full record id.

Writing a reliable scan request

Every sentence must match a recognised form. Write one read sentence, followed at the end by a colon and the comma-separated record ids (the same way the harness writes them). Use the full 36-character record ids, not a pair id, with no brackets or quotes. Two shapes are recognised:

  • look through, scan, check or review, followed by "these/the/those", an optional number, then parties, items, records, party records or item records, then "for duplicates", "for duplicate pairs" or "for duplicate records", and optionally ending with "and note / report / list what you find";
  • find, identify or list, followed by "duplicate" parties, items, records, party records or item records, then "in" or "among" "these/the/those", an optional number, and parties, items, records, party records or item records, optionally ending with "and note / report what you find" or "and record your merge proposal". Only this shape allows recording a proposal.

Naming both parties and items in one request is refused. "Records" alone means each id is looked up as a party first, then as an item. Safety sentences may stand alongside a scan or a recount, never alone: "Make no changes.", "Do not make any changes.", "Do not change any record." (or using delete, merge, create, update, edit, modify or remove; and record, item, party or approval request), "Leave every party record exactly as it is.", and the harness's own lists such as "Do not merge, delete, or change any record."

Exit codes and error lines

      

        
0Finished
A report or export completed, or a prompted run returned a done, failed, or refused claim.

        
1Could not run
Login fails or settings are missing; a platform outage or error occurs, including during a scan; a connection is lost; a recount table is cut off, or a field the rule needs is absent from every row of a non-empty table; or an export cannot run. Prints one line on standard error—such as could not run: …, platform problem: …, connection or file problem: …, or could not export: …—and never quotes a platform reply.

        
2Command-line mistake
Caused by an error such as an unknown --instance value. Shows the usage message.

      

      
Under the harness, an unexpected error shows as internal error: <error type>, while a local run shows the traceback. Because the harness treats a non-zero exit as an infrastructure failure, a scan that cannot read its records or runs out of time says so and exits 0, while a platform outage still exits 1.

      
On a single row, a missing contact, category, or vendor value counts as blank, and a party with no privacy state is left out of party recounts.

    

  


  

    

    

      
Limits worth knowing

      
    
        
  • Rule-based matching: Matching is by rules, so some duplicates are missed—such as spellings further apart than a letter or two ("Lakshmi" and "Laxmi"), abbreviations ("SS" for stainless steel), and initials.
    • 
        
  • Named-record scans: A scan compares only the records named, so its pairs can differ from the full report, which sees the whole table.
    • 
        
  • Fixed question wording: A reworded question is refused. New wording must be added to the agent and its tests.
    • 
        
  • Filled-in values in recounts: Recounts answer what is filled in, not what is true: a placeholder phone such as +91 0000000000 counts as a phone.
